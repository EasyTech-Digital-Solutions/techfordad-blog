# TechForDad

Static HTML affiliate blog reviewing tech products for seniors and their caregivers (US + Canada variants). No build step — pages are hand-authored HTML, deployed as static files via GitHub Pages (see `CNAME`).

## New article checklist

Every new `blog/*.html` article (weekly automated posts included) must ship with all of the following — not just the article body:

1. **The article HTML** in `blog/`, following the structure of a recent comparable article (head block with title/meta/canonical/og/twitter tags + `Article` JSON-LD, `.article-hero` section, comparison content, FAQ).
2. **Title ≤ 60 chars, meta description ≤ 160 chars.** Google truncates past this in search results — check actual character count, not a guess.
3. **A hero image.** See "Hero images" below — this step has been skipped on past articles and left them with a text-only hero and a broken/fallback `og:image`. Don't skip it.
4. **A card in `blog/index.html`** linking to the new article (match the existing `.card` markup; add `data-country="ca"` for Canada variants).
5. **A `sitemap.xml` entry** for the new URL.
6. **Run `python3 scripts/build_nav.py`.** The header's "All Reviews" dropdown is generated from `blog/*.html` (files ending `-canada.html` go under Canada, `noindex` pages are left out) and copied into every page. Re-run it after adding or removing an article so the menu and the cache-busting `?v=` on `style.css`/`main.js` stay in sync.
7. **Add the article to `scripts/build_related.py`** (a `TOPICS` entry, plus which topics it relates to in `RELATED`), then run `python3 scripts/build_nav.py`. It writes the "Keep Reading" block on every article and guide, so a new page is linked from at least two others and never left orphaned. If the new page is a US/Canada pair, also add it to `PAIRS` in `scripts/build_hreflang.py`. Never hand-edit the `<!-- related -->` or `<!-- hreflang -->` blocks.
8. **Green tests.** Run `tests/run.sh`; a new article must pass every check (title/description length, canonical, affiliate tags, accessibility baseline). If it adds a new kind of page or UI, update the tests too (see "Tests" below).

## Hero images

Every article hero should have a real photo, not just text on the navy background. Process (established in commits `c49f0f6`, `95d5905`):

1. Source a **copyright-free photo from Unsplash** (Unsplash License — free for commercial use, no attribution required) that matches the article's specific topic — not a generic tech stock photo.
2. Save it to `images/heroes/hero-<topic>.jpg`. Target ~900px wide, re-encoded as a progressive JPEG at quality ~82 (see commit `8326325`) — keep file sizes small, this is a full-bleed background image, not a print asset.
3. Wire it into the page in two places:
   - `<meta property="og:image" content="https://www.techfordad.com/images/heroes/hero-<topic>.jpg"/>` in the `<head>`.
   - `<img src="../images/heroes/hero-<topic>.jpg" alt="..." width="860" height="480" fetchpriority="high">` as the **first child** of `<div class="article-hero">`, before `.article-hero-inner`. (The CSS absolutely-positions it as a `background: cover`, so exact source dimensions don't matter — the `width`/`height` attributes are just layout-reservation hints and don't need to match the file's real pixel size. Use `fetchpriority="high"`, not `loading="lazy"`: the hero is the first thing visitors see, and lazy-loading it delays the page.)
4. **Run `python3 scripts/make_card_images.py`** so the new hero also gets a small WebP card thumbnail in `images/cards/` (the cards on the reviews index, homepage, gift hub and 404 load these, not the full hero). The card `<img>` in `blog/index.html` uses `../images/cards/hero-<topic>.webp`; the homepage and 404 use `images/cards/...`.
5. If no suitable photo exists yet, it's fine to ship the article with a text-only hero (many pages already work this way), but **come back and add one** — don't leave `og:image` pointing at a file that was never actually saved. If in doubt, point `og:image` at `images/og-default.svg` (the site's real fallback) rather than a hero filename that doesn't exist yet.

## Tests (read before changing any HTML, CSS or JS)

An automated suite in `tests/` checks every page: SEO basics, affiliate-link rules, security and privacy hygiene,
layout on desktop and phone in a real browser, every button and print path, print layout, accessibility, and (opt-in)
the live site. Full guide: `tests/README.md`.

- **Run `tests/run.sh` before every commit** that touches HTML, CSS, JS or `scripts/`. `tests/run.sh --quick` is the fast version.
  CI runs the whole suite on every pull request, so a red check blocks merging in practice.
- **When you change the UI, change the tests in the same pull request.** A new page type goes in `tests/pages.py`; a new
  CSS section needs a line in `tests/data/ui_components.json` plus a test that exercises it (the registry test fails
  until you do); a new button or behavior needs a test in `tests/test_ui_interactions.py`; a new Amazon link needs
  `tests/data/approved_amazon_links.json` and `python3 scripts/amazon_registry.py --update`.
- **Never make a failing test pass by loosening it or growing a baseline file** (`tests/data/known_issues.json`,
  `a11y_known_issues.json`). Fix the page, or ask first. Baselines only shrink.
- **`scripts/build_nav.py` rewrites every page.** To check without writing, use `python3 scripts/build_nav.py --check`.
  Bump `ASSET_VERSION` there whenever `css/style.css` or `js/main.js` changes (Cloudflare caches the versioned URLs).
- After merging to `main`, run `tests/run.sh --live` (the published site: uptime, certificate, security headers, and that
  internal files are not public). A weekly GitHub Action does the same.

## Content conventions

- **Canada and USA articles share one template** (two columns, sidebar, table of contents, author box, newsletter, click-to-open FAQ).
  The USA sidebar is hand-written; the Canada sidebar is generated by `scripts/build_ca_sidebar.py` (run by `build_nav.py`) from the
  page's own "Which One Should You Buy?" list and the topic map in `build_related.py`. A new Canada article needs an empty
  `<aside class="article-sidebar">` containing `<!-- ca-sidebar -->` / `<!-- /ca-sidebar -->`; copy an existing Canada article.
  FAQs use `div.faq-item > div.faq-q + div.faq-a` everywhere (not `<details>`, not bare `<h3>`). The order is the same on every article:
  "Which One Should You Buy?", the product cards, then "How They Compare Side by Side". Product cards, comparison tables, the disclosure box,
  the hero line (with "N min read") and the breadcrumb (`Home › Page`) are identical in markup between USA and Canada pages.
  `tests/test_template_parity.py` enforces all of this, so **never fix a layout problem on one country's pages only**: change both.
- US and Canada variants are separate files (`best-x-for-seniors.html` / `best-x-for-seniors-canada.html`), Canada pages use `lang="en-CA"` and CAD pricing.
- **Amazon affiliate tags:** US pages (amazon.com) use `tag=techfordad0b-20`; Canada pages (amazon.ca) use `tag=abhikar91-20`. Links inside the Gift Guides section (`gift-guides/`) use `tag=techfordad-gifts-20` instead of `techfordad0b-20`, so that section reports separately in Associates; never mix the two on one page. These are the only three registered tags. Never invent another (`techfordad-ca-20` was made up by past weekly runs and earns nothing). Before finishing, grep the new article for `tag=` and confirm every link uses the right one.
- **Internal files are not published:** the repository is public and GitHub Pages serves the whole repo, so `_config.yml` `exclude:` lists what must stay off the website (`CLAUDE.md`, `docs/`, `scripts/`, `admin/`, `newsletter-log.json`). Add any new internal file or folder there and check it returns 404 after publishing. Never put secrets, keys or customer data in the repo. The **admin panel is not served online**: run it locally (see `admin/README.md`).
- **Workflow dependencies are pinned:** GitHub Actions in `.github/workflows/` are pinned to full commit hashes and the price bot's Python package to an exact version in `scripts/requirements.txt`; Dependabot (`.github/dependabot.yml`) opens weekly PRs to update them. Review and merge those PRs; do not switch back to floating tags like `@v4` or an unpinned `pip install`.
- **Sources on guides:** `scripts/sources.json` lists the sources shown in the "Sources and Where to Check the Details" box at the bottom of a guide (`build_sources.py` writes it, before the Keep Reading box; currently medical alert, e-readers, blood pressure monitors, hearing aids (US, Canada and the guide), smartwatches, the fall prevention guide, Canada cell phones and Canada plans). Only add a link you have opened and that really covers the topic, and word `used_for` as what the page covers, never more. No Amazon links there (Check Price buttons carry the affiliate tag). Run `python3 scripts/build_sources.py --verify` monthly, and move `checked` forward only after that. CRTC and Canada.ca block scripted checks, so open those two in a browser.
- **Amazon link registry:** `scripts/amazon-registry.json` lists every distinct Amazon destination (id, product name, country, URL without the tag, ASIN, pages that use it). `python3 scripts/amazon_registry.py` (run by `check_site.py --all`) fails on any Amazon link that is not in the registry, a wrong tag for its section, or a store that does not match the page (Canada page = amazon.ca). After adding or changing an Amazon link, review it and run `python3 scripts/amazon_registry.py --update`, then commit the JSON diff.
- **GA4 affiliate click event:** `js/main.js` sends `amazon_affiliate_click` for every click on an amazon.com / amazon.ca link, with `product_name`, `article_slug`, `product_position` (1-based among the numbered product buttons, 0 otherwise), `cta_location` (`product_section`, `comparison_table`, `sidebar` or `inline`) and `country` (`US`/`CA`). These are registered as event-scoped custom dimensions in GA4 (Article slug, CTA location, Product name, Product position, Store country), so keep the parameter names unchanged. It measures outbound clicks only, never purchases or commission. It reads the `data-cta` / `data-product` attributes that `scripts/standardize_ctas.py` and `scripts/build_buying_summary.py` write on the buttons. After editing `js/main.js`, raise `ASSET_VERSION` in `scripts/build_nav.py` and run `python3 scripts/build_nav.py` so browsers fetch the new file.
- **Amazon buttons and decision sections:** every `btn-check-price` link reads "Check Price on Amazon →" ("...Amazon.ca →" on Canada pages) and carries an `aria-label` and `data-cta`/`data-product` attributes; `scripts/standardize_ctas.py` enforces this and runs from `build_nav.py`. The "Which One Should You Buy?" section and the button after the comparison table come from `scripts/build_buying_summary.py` (add a page to its `PAGES` map); never hand-edit the `<!-- buy-summary -->` / `<!-- table-cta -->` blocks.
- **Product schema:** `scripts/build_product_schema.py` reads each article's own `.product-card` markup (name, price spec, Amazon link) and writes an `ItemList` of `Product`/`Offer` JSON-LD into a `<!-- product-schema -->` block in `<head>`; it runs from `build_nav.py` and is checked by `check_site.py --all`. Deliberately no `review`/`aggregateRating`: TechForDad does not test products, so any score would be an opinion, and tagging it as a rating would misrepresent it to Google. The invented "Our Score X/10" values were removed on 2026-10-05; do not add numeric scores or star ratings (`test_content_rules.py` fails on them). A card with no clean price (e.g. "varies by package") gets a bare `Product` with no `Offer`, never an invented price. Never hand-edit the `<!-- product-schema -->` block; add a new "Best X" article's cards and rerun instead.
- **Amazon disclosure:** Amazon requires the exact sentence "As an Amazon Associate I earn from qualifying purchases." It lives in the `footer-affiliate` paragraph in the site footer. Copy the footer unchanged from an existing page and confirm the sentence is present on every new article.
- Product prices are kept current by the monthly claude.ai routine ("TechForDad — Monthly Content & Price Audit", 1st of the month, trigger id `trig_011GpnkjuXq9iPbi9jcVX1t9`), which verifies every product via `scripts/price-sources.json` with real `WebFetch`/news checks, fixes mechanical on-page SEO issues (`check_site.py --all`, including `check_internal_links.py`), keeps the Amazon registry and homepage product count current (`amazon_registry.py --update`, `update_site_stats.py`), reports (but never auto-advances) the guides' source-link health (`build_sources.py --verify`), runs a post-push site-health smoke check against the live site, and commits fixes directly. It self-checks every run for any blog/guides page that's never been audited, since the topic-group lists below are a common-case guide, not the authoritative scope. `scripts/products.json` and `scripts/auto_price_update.py` (GitHub Action `auto-price-update.yml`) are a mechanical dollar-amount-swap bot that ran weekly until 2026-09-30; its schedule is retired (superseded by the monthly routine's real verification) and it's now `workflow_dispatch`-only for an occasional manual spot-fix. Whichever one touches a price, run `build_product_schema.py` right after so the `<!-- product-schema -->` JSON-LD stays in sync (`check_site.py --all` catches it if you forget). `gift-guides/*.html` prices get the same monthly treatment as an 8th group (Step 3.6 of the routine's prompt): research each distinct product once across all 6 guides, verify it the same way as everywhere else (fetch the manufacturer's page, or two independent sources within 60 days), edit the `GUIDES` list in `build_gift_guides.py`, confirm each ASIN is still a live/buyable listing with `check_amazon_listings.py`, then run `build_gift_guides.py --checked YYYY-MM-DD` only if something was actually re-verified. Never hand-edit `gift-guides/*.html` directly, including from this routine.
- **Internal link check:** `scripts/check_internal_links.py` resolves every root-relative and relative `href` against the site root and fails on any that don't exist. Runs from `check_site.py --all`; a broken internal link wastes crawl budget and is cheap to catch here instead of waiting on Search Console.
- **Monthly audit dashboard:** each monthly run writes `docs/audit-reports/latest.json` (this run) and prepends to `docs/audit-reports/history.json` (last 12 runs) — status, groups audited, what changed, what needs human review, content-freshness flags, and the post-push site-health result. `docs/` is excluded from the published site but still readable at `raw.githubusercontent.com/.../main/docs/audit-reports/latest.json` (raw git blobs bypass the Pages/Jekyll exclude). A published dashboard artifact fetches those two files client-side on load, so the site owner can check audit status from one bookmarked page instead of the repo. Never hand-edit `latest.json`/`history.json` outside the routine; if its schema changes, update both the routine's prompt (via `RemoteTrigger action=update`) and the dashboard's fetch/render code together.

## Health content, sources and honesty (added 2026-10-05)

- **Health, tax, insurance and government-program statements need a source you have opened.** Follow `docs/medical-content-process.md`: verify against a primary source, link it inline (`target="_blank" rel="noopener"`), add it to `scripts/sources.json`, soften or remove what the source does not say, and never cite a page you could not open (heart.org, mayoclinic.org, validatebp.org, canada.ca, cdc.gov block scripted reads: open them in a browser). Check the CRA guide before saying anything is claimable on a Canadian tax return (blood pressure monitors and personal response systems are NOT).
- **Never claim experience or testing the site does not have** ("we've seen", "in our experience", "we tested", numeric scores, "industry-leading"). The site says it does not test products; `tests/test_content_rules.py` enforces it. Attribute maker claims to the maker ("Oticon says").
- **`scripts/build_health_note.py`** puts the "not medical advice" line inside the affiliate box on every page in its `MEDICAL_PAGES` list; add a new medical page there. **`scripts/build_faq_schema.py`** writes FAQPage JSON-LD from the visible FAQ; never hand-edit the schema. Both run from `build_nav.py`.
- **`scripts/build_gift_guides.py` is out of sync with the committed gift guides** (it does not write the Prime/Audible/Music bounty links or the Sep 30 price date). Running it deletes them. Edit gift guides by targeted patch and run `python3 scripts/amazon_registry.py` afterwards.
- **robots.txt must not Disallow a folder whose pages rely on `noindex`** (the old stub folders): Google cannot see a noindex on a blocked page. A test enforces it.
- **Social cards:** every indexable page needs a JPG/PNG `og:image` (SVG is ignored by social platforms; `images/og-default.png` is the fallback), `twitter:card` `summary_large_image`, and the matching `twitter:image`.

## Gift Guides, seasonal themes and site chrome

- **Gift Guides** live in `gift-guides/`. Their content is defined in `scripts/build_gift_guides.py` (products, ASINs, prices, FAQs). Edit that file and run `python3 scripts/build_gift_guides.py`; it rewrites the six pages, the "See more gift ideas" boxes on the review pages, and the sitemap entries, then runs `build_nav.py`. Do not hand-edit `gift-guides/*.html` EXCEPT while the generator is out of sync (see the warning under "Health content, sources and honesty": until it is fixed, use a targeted patch and run `amazon_registry.py`).
- Gift Guides links use `tag=techfordad-gifts-20` only (see the affiliate tags rule above). Write prices as "about $X (source, checked date)" and never as a live price.
- Before publishing or refreshing a guide, run `python3 scripts/check_amazon_listings.py out.json ASIN ...` to confirm each listing is live, buyable and well rated. Amazon rate-limits after roughly 100 rapid requests; wait a while if it reports `blocked`.
- **Seasonal themes:** `js/season.js` sets `data-season` (Halloween Sep 29 - Oct 31, Christmas Nov 1 - Dec 31) and `data-gifts` (big gift banner Sep 1 - Dec 31, May 1-14, Jun 1-21). Colours are variables in `css/style.css`; outside the windows the default look is used. Preview with `?season=halloween|christmas|none` and `?gifts=peak|off`.
- **Header menus** (All Reviews, Gift Guides, Guides, About) are generated into every page by `scripts/build_nav.py`. Re-run it after adding or removing any article, guide or gift guide. Redirect stubs (pages with `http-equiv="refresh"`) and `noindex` pages are left out of the menus.
- `guides/best-senior-gifts.html` is a redirect stub to the Gift Guides hub. Do not recreate a competing gifts page.
- Hero images use `fetchpriority="high"`, never `loading="lazy"`.
- The monthly price audit (`scripts/audit_inventory.py`) covers `blog/`, `guides/` and `gift-guides/`.
- **Dates and counts that must not go stale:** the gift guides take every date from one setting in `scripts/build_gift_guides.py`; after re-checking prices, run `python3 scripts/build_gift_guides.py --checked YYYY-MM-DD` (this updates "Updated ...", the price notes and the structured-data date together). Do not run it unless prices were actually re-checked. Run `python3 scripts/update_site_stats.py` to refresh the homepage "N+ Products Compared" claim. Never change an "Updated" date without changing the content.
- **Gift announcement bar** (`<!-- gift-bar -->`, injected on every page except `gift-guides/` by `build_nav.py`) shows only while `data-gifts="peak"`. Visitors can dismiss it (remembered 14 days in `localStorage`); preview with `?giftbar=show`. The homepage picture tiles are generated by `build_gift_guides.py` from the same guide data, with price chips in its `CHIPS` table; update those chips when the lowest verified price in a guide changes.
